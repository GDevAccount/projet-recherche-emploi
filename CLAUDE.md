# CLAUDE.md

Agent de recherche d'emploi : un graph LangGraph cherche des offres avec Tavily, les filtre avec un modèle OpenAI selon le CV, et les stocke en SQLite. Un serveur FastAPI expose le tout par une API, et un front Angular (`frontend/`), servi par ce même serveur, est la seule interface. Le README décrit l'usage ; ce fichier ne couvre que ce qu'il faut savoir pour modifier le code.

## Commandes

Toutes se lancent depuis la racine du projet, car `jobs.db` est un chemin relatif au dossier courant.

```bash
uv sync                                                   # installer les dépendances
uv run projet-recherche-emploi                            # recherche seule, sans le serveur
uv run projet-recherche-emploi api                        # serveur de développement sur http://127.0.0.1:8000 (documentation : /docs)
uv run projet-recherche-emploi serve                      # serveur tel qu'en ligne : toutes les interfaces, sans la documentation
uv run projet-recherche-emploi graph                      # régénérer graph.png (service en ligne mermaid.ink)
uv run projet-recherche-emploi migrate                    # créer la base ou l'amener au dernier schéma
uv run projet-recherche-emploi purge                      # supprimer les comptes d'invités inactifs (fait aussi par le serveur, une fois par jour)
uv add <paquet>                                           # ajouter une dépendance
```

```bash
uv run pytest                                             # tests, sur une base temporaire
uv run ruff check .                                       # linter
uv run alembic revision --autogenerate -m "..." --rev-id 0006   # écrire une migration (voir Pièges)
```

Le front se pilote depuis `frontend/` (Node 22.22.3 ou plus récent) :

```bash
npm ci                                                    # installer les dépendances
npm start                                                 # http://localhost:4200, /api relayé vers le serveur de développement (port 8000)
npm test -- --watch=false                                 # tests (Vitest)
npm run lint                                              # linter
npm run build                                             # build, servi ensuite par le serveur Python à la racine
npm run e2e                                               # tests de bout en bout (Playwright), après un build
```

Les tests (`tests/`) couvrent le schéma et les migrations, le cloisonnement entre utilisateurs, les services, le graph avec de faux Tavily et OpenAI, l'API, le service du front (`test_frontend.py`) et le sens des imports entre couches (`test_architecture.py`). Ils construisent leur application avec `build_container()` (fixtures de `tests/conftest.py`).

Les tests de bout en bout (`frontend/e2e/`, Playwright) déroulent un parcours complet dans le Chrome de la machine : connexion, dépôt du CV, recherche, suivi des offres, rejets, déconnexion. Playwright lance lui-même `tests/e2e_server.py`, l'application entière sur une base temporaire avec les faux Tavily et OpenAI, et sert le front tel qu'il est dans `frontend/dist/` : reconstruire avant de les lancer. Les scénarios se suivent et partagent leur état. Leurs fichiers se terminent par `.e2e.ts`, pas `.spec.ts`, réservé aux tests unitaires. Ils échouent aussi si la politique de contenu refuse une ressource pendant le parcours.

Les clés `TAVILY_API_KEY` et `OPENAI_API_KEY` sont lues dans `.env` (modèle : `.env.example`), chargé par `load_dotenv()` dans les points d'entrée (`cli.py`, `create_app()` de `api/main.py`). Ne jamais afficher ni committer le contenu de `.env`.

Les autres variables sont les champs de `Settings` (`config.py`) : `DATA_DIR` déplace `jobs.db` vers un volume (voir `Dockerfile`), `FRONTEND_DIR` dit où est le front construit, `APP_PASSWORD` est le mot de passe de l'instance. `GOOGLE_CLIENT_ID` active la connexion Google, qui demande aussi `OWNER_EMAIL` ; `ALLOWED_EMAILS` liste les invités, ou vaut `*` pour accepter tout compte Google (voir le README). `AUTH_COOKIE_SECRET` signe le cookie de session : il est obligatoire dès qu'un mot de passe ou la connexion Google est défini. `CORS_ORIGINS` liste les sites autorisés à appeler l'API depuis un navigateur, ce qui ne sert que si le front est hébergé ailleurs.

L'instance en ligne tourne sur Fly.io (`fly.toml`) et sert, dans un seul processus et à une seule adresse, l'API sous `/api`, les pages légales et le front Angular à la racine. Elle est publiée automatiquement à chaque push sur `main` par `.github/workflows/fly-deploy.yml`, après le linter et les tests des deux côtés, le build du front et les tests de bout en bout ; `fly deploy --build-arg PRIMEUI_LICENSE=…` reste possible à la main, sans ce contrôle. Les clés API et `APP_PASSWORD` y sont des secrets Fly, pas un `.env`. Le jeton utilisé par le workflow est le secret GitHub `FLY_API_TOKEN`.

## Architecture

Le code du serveur est dans `src/projet_recherche_emploi/`, celui du front dans `frontend/`. Les dépendances ne vont que vers le bas, et `tests/test_architecture.py` le vérifie :

```
   api/   cli.py           interfaces : aucune règle métier
        │
   container.py            assemblage : relie réglages, base, graph et services
        │
   services/   agent/      règles métier ; recherche LangGraph
        │
      data/                seuls accès à SQLite et aux fichiers
```

`config.py`, `errors.py` et `schemas.py` sont importables partout.

- `container.py` est le seul endroit où les objets sont reliés. `Container` crée la base, le stockage des CV, le graph et les services ; `get_container()` renvoie celui du processus, `build_container()` en construit un autre (tests). Un service ou un nœud reçoit ce dont il a besoin à sa construction : il n'importe ni chemin de base ni client.
- `api/` est le serveur FastAPI, seule couche autorisée à importer `fastapi`. `main.py` le construit (`create_app`, et `create_server_app` pour la version en ligne, sans documentation) et traduit les erreurs en codes HTTP, `security.py` identifie l'appelant, `routers/` contient les routes, toutes sous `/api`. `public_pages.py` sert les pages légales en HTML simple, parce que les robots de Google ne lisent pas une page qui demande du JavaScript. `frontend.py` sert les fichiers du front construit, à la racine.
- `services/` porte les règles métier, dans une classe par domaine : `AuthService` (quel utilisateur pour une adresse Google, mot de passe de l'instance), `AccountService` (suppression d'un compte), `SearchService` (conditions préalables, quota, lancement du graph), `CvService` (dépôt d'un CV, oubli des rejets de l'ancien, lecture de son texte), `JobService` et `QueryService` (offres, pages rejetées, postes recherchés). Les interfaces ne passent que par eux.
- `agent/` est la recherche LangGraph. `graph.py` construit le graph : `searchJobs` → `FilterDuplicates` → `FilterJobs` → `InsertJobs`. Les quatre nœuds sont les méthodes de `SearchNodes` (`nodes.py`), l'état partagé est dans `state.py`, le prompt du filtre dans `prompts.py`. `ports.py` décrit ce que le graph attend de l'extérieur (un moteur de recherche, un évaluateur, un lecteur de CV) et `adapters.py` en donne les versions réelles, Tavily et OpenAI.
- `data/` regroupe les seuls accès à SQLite et aux fichiers, avec SQLAlchemy. `models.py` décrit les tables, `database.py` ouvre les sessions et applique les migrations de `migrations/` (Alembic). `repositories/` contient un dépôt par table : `job_repository.py`, `rejected_job_repository.py`, `query_repository.py`, `user_repository.py`, `search_run_repository.py` et `cv_text_repository.py` servent respectivement `jobs`, `rejected_jobs`, `search_queries`, `users`, `search_runs` et `cv_texts`. `cv_ingestion/` mène un CV du PDF déposé au texte enregistré : `pdf_reader.py` lit le PDF, `anonymizer.py` en retire les coordonnées, `ingestion.py` enchaîne les deux et écrit dans `cv_texts`.
- `schemas.py` définit les objets que les services renvoient (Pydantic) : l'API les sert tels quels en JSON.
- `errors.py` définit les erreurs destinées à l'utilisateur.
- `config.py` regroupe les réglages : `Settings` pour les variables d'environnement, des constantes pour le reste (modèle, sites, quota, recherches par défaut).
- `cli.py` est la commande `projet-recherche-emploi`.

Le front Angular est hors de ce paquet, dans `frontend/` : composants autonomes en `OnPush`, état en signaux, dépendances par `inject()`, composants PrimeNG. Il ne connaît que l'API.

## Pièges

- **Un import ne doit rien déclencher.** Le conteneur est construit au premier appel de `get_container()`, le graph à la première recherche, les clients Tavily et OpenAI à leur premier usage, et les logs sont réglés par `configure_logging()` dans chaque point d'entrée. Ne pas remettre d'appel réseau, d'accès à la base, de `load_dotenv()` ni de `basicConfig` au niveau d'un module. Pour l'API, c'est `create_app()` qui fait tout : le serveur la lance en mode « factory ».
- **Les réglages sont lus une fois.** `Settings()` lit les variables d'environnement à la construction du conteneur : en changer une demande de redémarrer. Un test ne modifie pas l'environnement, il passe ses réglages à `Settings(...)` ; la fixture `clean_environment` efface ceux de la machine.
- **Une vraie recherche coûte de l'argent.** Chaque exécution du graph consomme des crédits Tavily et OpenAI. Ne pas la lancer pour vérifier un changement sans l'accord de l'utilisateur ; tester avec `FakeSearchEngine` et `FakeEvaluator` de `tests/conftest.py`.
- **Changer le schéma demande une migration.** Modifier `data/models.py` n'a aucun effet sur un `jobs.db` existant. Il faut une migration Alembic dans `data/migrations/versions/`, écrite avec `alembic revision --autogenerate` puis relue. `test_schema.py` échoue si les modèles et les migrations ne décrivent plus le même schéma. L'application applique les migrations en attente à la construction du conteneur, et l'image Docker le fait avant de servir (`projet-recherche-emploi migrate` dans le `Dockerfile`) : une migration qui échoue arrête le déploiement au lieu de casser la première visite. La base du volume Fly.io ne se migre que par ce biais.
- **Une migration est copiée d'abord, et tient en une transaction.** Avant d'en appliquer une à une base existante, `Database.migrate()` copie la base dans `jobs.avant-migration-<version>.db`, à côté d'elle. `database.py` fait émettre le `BEGIN` par SQLAlchemy, parce que le pilote `sqlite3` n'en ouvre pas pour un `CREATE` ou un `ALTER` : ne pas retirer `_use_explicit_transactions`. Ces copies contiennent les données de tous les utilisateurs : les supprimer une fois la migration vérifiée. La suppression d'un compte retire ses données de chacune sans les effacer (`Database.purge_user_from_backups`) : elles restent le seul moyen de revenir en arrière après une migration ratée.
- **La première migration ne crée que les tables manquantes.** Avant Alembic, chaque dépôt créait sa table à son premier usage : une base ancienne peut ne pas avoir `users` ni `search_runs`. `0001_schema_initial.py` teste donc chaque table. Les migrations suivantes n'ont pas à le faire.
- **Les colonnes gardent les types d'avant SQLAlchemy.** Les dates sont du texte UTC au format de `CURRENT_TIMESTAMP`, les booléens des entiers : `UtcDateTime` et `IntBool` de `models.py` font la conversion. Utiliser ces deux types pour toute nouvelle colonne de date ou de booléen, sinon les comparaisons de dates en texte ne tiennent plus.
- **Toute requête SQL doit filtrer sur `user_id`.** Chaque dépôt reçoit la session et l'utilisateur à sa création (`JobRepository(session, user_id)`) et ne lit ni ne modifie que ses lignes. Une requête écrite sans `user_id` montrerait les données d'un utilisateur à un autre : `tests/test_user_isolation.py` couvre chaque méthode publique, ajouter un cas pour toute nouvelle méthode. Seul `UserRepository` n'a pas d'utilisateur. Sans connexion Google, l'utilisateur est `DEFAULT_USER_ID` (1) : l'application reste mono-utilisateur.
- **Un seul processus sert tout.** `create_app()` assemble l'API, les pages légales et le front, autour d'un même conteneur, donc des mêmes réglages et de la même base. Ne pas les séparer en deux processus ou deux machines tant que la base est un fichier SQLite.
- **La documentation de l'API n'est pas servie en ligne.** `/docs` et `/openapi.json` décrivent toutes les routes à qui n'est pas connecté : la commande `serve` passe par `create_server_app()`, qui les retire, et seule la commande `api`, liée à `127.0.0.1`, les garde. Ne pas faire servir `create_app` par le `Dockerfile`.
- **Une connexion à moitié réglée arrête le serveur.** `AuthService.check_configuration()` refuse `GOOGLE_CLIENT_ID` sans `OWNER_EMAIL`, et un mot de passe ou la connexion Google sans `AUTH_COOKIE_SECRET`. Il est appelé par `migrate`, donc par l'image Docker avant de servir, et par `create_app()` au démarrage : sans lui, l'instance démarrerait et refuserait tout le monde. Les tests construisent leur conteneur sans passer par là.
- **Les réponses sont compressées, sauf le flux d'une recherche.** `GZipMiddleware` (`api/main.py`) laisse passer `text/event-stream` tel quel : compressé, le flux serait retenu jusqu'à la fin et le suivi n'arriverait plus en direct. `test_api.py` le vérifie.
- **Le navigateur refuse tout script qui ne vient pas du site.** `SecurityHeadersMiddleware` (`api/security_headers.py`) pose la politique de contenu sur chaque réponse : seuls les scripts du site et celui du bouton Google sont acceptés, aucun script écrit dans la page. Charger une ressource d'un autre site demande de l'y ajouter. C'est pour cela que `angular.json` désactive `inlineCritical`, qui ajoutait un script à `index.html`. Vérifier un changement en lisant la console du navigateur : une ressource refusée n'apparaît que là.
- **Le front reçoit ce que rien d'autre n'a pris.** Sa route (`api/frontend.py`) est ajoutée en dernier et renvoie la page d'accueil à toute adresse inconnue, que le routeur d'Angular résout. Deux exceptions restent des erreurs 404 : un fichier manquant (une adresse avec une extension), et une adresse sous `/api`. Une nouvelle route du serveur hors de `/api` doit donc être ajoutée avant elle. L'ancienne adresse `/frontend/…` redirige vers la racine.
- **Un fichier du front dont le nom porte une empreinte est gardé un an par le navigateur.** `api/frontend.py` le reconnaît à son nom (`main-5UFRYBOQ.js`) et le sert en `immutable` ; la page d'accueil est redemandée à chaque visite. Un fichier de `frontend/public/`, sans empreinte, ne doit donc pas se terminer par un tiret suivi de huit caractères.
- **Le front est à la racine, et sans build il n'existe pas.** `baseHref` vaut `/` dans `frontend/angular.json`. Sans `frontend/dist/` (ou `FRONTEND_DIR`), le serveur n'a pas de route pour lui et ne répond que par l'API : c'est le cas des tests, dont `make_client` écarte le build éventuel de la machine.
- **Les fichiers du front sont publics.** Ils sont servis sans connexion : ne rien y mettre de secret, ni dans `environment.ts`. Ce sont les routes de l'API qui protègent les données.
- **Le front ne garde aucune preuve d'identité.** Le jeton Google ou le mot de passe ne sert qu'à `POST /api/session` (`SessionService.open`), puis le cookie `HttpOnly` prend le relais : ne rien mettre dans `localStorage`. Les gardes de route (`core/auth.guard.ts`) évitent seulement un écran vide ; la protection, c'est l'API. Un 401 sur un appel de données renvoie à l'écran de connexion (`core/api.interceptor.ts`).
- **Le bouton Google du front dépend de la console Google.** Il passe par Google Identity Services (`core/google-identity.service.ts`), qui exige l'adresse du site dans les « origines JavaScript autorisées » de l'ID client. Changer d'adresse, ou externaliser le front, demande de l'y ajouter.
- **Le nom affiché, Tamis, est celui déclaré à Google.** La validation de l'écran de connexion compare le nom saisi dans la console Google (page « Branding ») à celui de la page d'accueil lue sans JavaScript (`frontend/src/index.html`) : changer l'un demande de changer l'autre. Le paquet, le dépôt et l'instance Fly.io gardent le nom `projet-recherche-emploi`.
- **Le front a son identité visuelle.** Encre et citron vert, thème clair et sombre. Les couleurs de l'application sont les variables `--app-*` de `frontend/src/styles.scss`, celles des composants PrimeNG viennent de `AppPreset` (`core/theme.ts`) : changer une teinte demande de regarder les deux. Le thème sombre est la classe `app-dark` sur `<html>`, posée par `ThemeService`, et avant lui par `frontend/public/theme-init.js`, pour qu'aucune page claire n'apparaisse au chargement : les deux appliquent la même règle, changer l'une demande de changer l'autre. Les pages légales recopient ces couleurs (`PAGE_STYLE` de `api/public_pages.py`), parce qu'elles sont servies sans le front ni JavaScript : leur thème sombre suit le système, pas le choix fait dans l'application. L'icône mobile et le manifeste (`frontend/public/`) portent aussi le citron vert et l'encre. Un nouvel écran se vérifie par capture d'écran dans les deux thèmes et en largeur mobile.
- **Le front ne décide rien.** Un calcul dont un écran a besoin s'écrit dans un service Python, et l'API le renvoie. L'adresse de l'API vient de `environment.apiUrl`, jamais d'une chaîne en dur : en local comme en ligne, elle vaut `/api`, et c'est `proxy.conf.json` qui relaie vers le port 8000 avec `npm start`.
- **La clé de licence PrimeNG n'est pas dans le dépôt.** Le dépôt est public : elle arrive au build par `--define PRIMEUI_LICENSE` (`frontend/src/environments/license.ts`), depuis le secret GitHub `PRIMEUI_LICENSE` et l'argument de build du `Dockerfile`. Sans elle, tout fonctionne mais PrimeNG affiche un bandeau « licence invalide » : c'est le cas en local et dans les tests. Elle expire le 2027-10-08 et se renouvelle sur primeui.dev. Un `fly deploy` à la main doit la passer par `--build-arg`.
- **Toute route de l'API passe par `UserId`.** C'est la dépendance de `api/security.py` qui identifie l'appelant ; une route sans elle serait ouverte à tous. `test_api.py` liste les routes protégées et échoue si une route n'y figure pas. Deux routes sont publiques, `GET /api/health` et `GET /api/config` : la seconde dit au front comment se connecter, et ne doit rien renvoyer de secret (`test_config_leaks_no_secret`). Sans connexion Google ni `APP_PASSWORD`, l'API refuse tout (503) : ne pas lui donner d'accès par défaut à l'utilisateur 1.
- **Le cookie de session de l'API porte une adresse, pas un utilisateur.** `POST /api/session` échange un jeton Google (ou `APP_PASSWORD`) contre un jeton signé par `AuthService` avec `AUTH_COOKIE_SECRET`, posé dans un cookie `HttpOnly`. Chaque requête repasse par `resolve_user_id` : ne pas y mettre l'identifiant de l'utilisateur, sinon un invité retiré de `ALLOWED_EMAILS` garderait son accès 30 jours. Une session ne s'ouvre qu'avec l'en-tête `Authorization`, jamais avec un cookie, pour qu'un cookie volé ne puisse pas se prolonger. Le jeton porte aussi le nom et la photo du profil Google, pour la vignette de l'en-tête : ils ne donnent aucun droit et ne sont enregistrés nulle part ailleurs.
- **Une route qui modifie des données n'utilise pas `GET`.** Avec le cookie, `_check_origin` de `api/security.py` refuse les requêtes venues d'un autre site, sauf pour `GET`, `HEAD` et `OPTIONS`, supposées sans effet.
- **Les fichiers du front ne protègent rien.** Ils sont servis sans connexion, comme les routes HTML de `api/public_pages.py` (`/confidentialite`, `/conditions`, fichier de validation Google), et aucun ne touche aux dépôts. Les gardes de route d'Angular évitent seulement un écran vide : toute donnée passe par une route de l'API, qui exige une identité.
- **Un objet lu en base ne sort pas de sa session.** Un service convertit les lignes en schémas Pydantic (`JobRead.model_validate(...)`) avant de fermer la session. Les interfaces ne voient jamais un modèle SQLAlchemy.
- **Le modèle ne reçoit jamais le texte brut du CV.** Au dépôt, `CvIngestion.ingest` (`data/cv_ingestion/`) passe le texte du PDF par `CvAnonymizer` et l'écrit dans `cv_texts` ; le graph le lit par le port `CvReader`, servi par `CvService.read_text`. Le nom n'est connu qu'au dépôt (nom du compte Google, donné par la route). Les motifs retirent ce qui a la forme d'une coordonnée et, dans le doute, laissent le texte : un nouveau motif s'ajoute avec ses cas dans `tests/test_cv_anonymizer.py`, y compris ce qu'il ne doit pas toucher. Changer un motif ne récrit pas les textes déjà enregistrés, et rien ne permet de les recalculer : le PDF n'existe plus, seul un nouveau dépôt applique le nouveau motif.
- **Le PDF d'un CV n'est pas conservé.** Il est lu en mémoire au dépôt, et seul son texte sans coordonnées est gardé, dans `cv_texts` : c'est le CV de l'utilisateur. Sa colonne `updated_at` dit qu'un CV est en place et depuis quand (`CvService.get_status`, `SearchService.can_search`). Ne pas vider cette table pour forcer un recalcul : ce serait effacer les CV. Les versions précédentes gardaient le fichier, `cv.pdf` pour l'utilisateur 1 et `cv/<identifiant>.pdf` pour les autres : `absorb_legacy_cv_files` (`data/cv_ingestion/legacy_files.py`), appelé par `build_container()`, enregistre le texte de ceux qui ne l'étaient pas, puis supprime ces fichiers. Il supprime donc tout `cv.pdf` posé dans `DATA_DIR`.
- **Les recherches par défaut ne vont qu'à l'utilisateur 1, une seule fois.** `DEFAULT_QUERIES`, calé sur le profil de l'auteur, est écrit en base par la première migration, à la création de la table `search_queries`. C'est voulu : une recherche supprimée par l'utilisateur ne doit pas revenir, et un autre utilisateur part d'une liste vide.
- **Une offre a deux identités.** Son `id` la désigne dans l'API et le front ; le couple utilisateur + URL, resté unique, sert à reconnaître une offre déjà vue. Ne pas retirer cette contrainte : `insert_jobs` s'appuie dessus pour ignorer les doublons.
- **Le contrat d'une offre est celui de la page, pas celui de la recherche.** Le type de contrat d'une recherche enregistrée complète le texte envoyé à Tavily (`build_search_text` de `agent/nodes.py`). Celui d'une offre est lu sur la page par le modèle (`JobEvaluation.contract_type`) et vaut `None` si elle ne le dit pas. Une seule règle écarte une offre pour son contrat, et c'est le graph qui l'applique (`contract_is_accepted`) : un stage ou une alternance (`TRAINING_CONTRACTS`) qu'aucune recherche ne demande. Les autres contrats ne sont pas tranchés, parce qu'une recherche de CDI ramène aussi des missions. Les lignes d'avant ce changement portent le contrat de leur recherche.
- **Supprimer une offre ne supprime pas sa ligne.** `delete_jobs` passe `deleted` à 1 et `list_jobs` masque ces lignes. C'est voulu : l'URL reste en base, donc l'insertion ignore l'offre à la recherche suivante. Toute lecture de `jobs` destinée à l'affichage doit filtrer sur `deleted` ; `list_known_urls` ne filtre pas, exprès, pour que le nœud `FilterDuplicates` écarte aussi les offres supprimées avant l'appel au modèle.
- **Un rejet est mémorisé, sauf s'il ne tient qu'aux recherches.** `InsertJobs` écrit les pages rejetées dans `rejected_jobs`, et `FilterDuplicates` écarte leurs URL pour ne pas payer une seconde évaluation. `CvService.save_cv` vide la table à l'enregistrement d'un nouveau CV. `QueryService.add_query` n'oublie que les rejets qui dépendent des recherches (métier, contrat, lieu) et dont le CV convenait. Après un changement de `FILTER_PROMPT`, les anciens rejets restent : il faut vider la table à la main pour les faire réévaluer.
- **Le modèle rapporte, le graph décide.** `JobEvaluation` (`agent/ports.py`) contient des faits lus sur la page et trois avis : `matches_search` (le métier est-il l'un de ceux des recherches, quel que soit le CV), `matches_skills` et `matches_level`. `judge` de `agent/nodes.py` en tire le verdict critère par critère, y ajoute les règles de contrat et de lieu, et une offre n'est retenue que si tout est vrai. Le détail est enregistré dans `rejected_jobs`, et `RejectedJobRead` (`schemas.py`) en tire le motif affiché (`motive`, `failed_criteria`), que l'API renvoie tel quel : ne pas le recalculer dans une interface ; `matches_cv` y réunit compétences et niveau. Les tolérances (technologie voisine acceptée, quelques années d'écart, doute sur le métier = rejet) sont celles du propriétaire, écrites dans `FILTER_PROMPT` : elles valent pour tous les utilisateurs. Une règle qui dépend des recherches s'écrit dans le graph à partir de `SearchCriteria`, pas dans le prompt.
- **Le texte envoyé à Tavily n'est pas la phrase saisie.** `build_searches` de `agent/nodes.py` la fait précéder de « offre d'emploi » et suivre du contrat et du lieu : mesuré en ligne le 2026-10-08, « Ingénieur IA » seul ramenait 14 listes d'offres sur 15 pages. Une recherche `remote` part une seconde fois, en anglais et sans ces mots français (`build_international_search_text`), sur `JOB_SITES` et `REMOTE_JOB_SITES` : le port `JobSearchEngine.search` reçoit `international=True`. La colonne `query` d'une offre garde la phrase saisie.
- **Le lieu se juge sur toutes les recherches à la fois.** Une recherche enregistrée vise un lieu (`location`), le télétravail complet (`remote`, sans limite de pays) ou, sans l'un ni l'autre, toute la France. Comme un verdict est mémorisé par URL et non par recherche, une page n'est pas jugée sur le lieu de la recherche qui l'a trouvée, mais sur ceux de toutes les recherches de l'utilisateur. Le modèle ne décide pas : il rapporte la ville, le pays et le mode de travail de l'offre, et dit seulement si ce lieu est dans les zones géographiques acceptées (`describe_accepted_areas` de `agent/nodes.py`). C'est `location_is_accepted` qui applique les règles : un poste en télétravail complet passe dès qu'une recherche `remote` existe, sauf si la page le réserve aux candidats d'un pays sans la France (`open_to_candidates_in_france`) ; sinon il faut que le lieu soit dans une zone acceptée, y compris pour un poste à distance trouvé sans recherche `remote`. La consigne de zone du prompt est écrite par `describe_area_rule` de `agent/prompts.py`, pour que le modèle n'ait aucune condition à résoudre. Une page écartée ainsi est rejetée avec `matches_location` à faux. `QueryService.add_query` oublie ces rejets-là (`clear_search_dependent_rejections`), puisque la nouvelle recherche peut les accepter ; ceux d'avant la migration 0003, classés « pas une offre », restent. Le lieu affiché d'une offre (`work_location`) est composé par `format_work_location` à partir de ce que le modèle a lu : la ville, ou « Remote » suivi de la ville de l'employeur.
- **Le quota est compté avant la recherche, après les conditions préalables.** `SearchService.stream_search` refuse d'abord une recherche sans CV ou sans poste recherché, puis enregistre le lancement, puis lance le graph : une recherche qui échoue en route a pu consommer des crédits, donc compte. Le refus est levé à l'appel, avant le premier élément du déroulement, pour que l'API puisse encore répondre par une erreur. Le quota (`MAX_SEARCHES_PER_DAY`) ne s'applique pas à l'utilisateur 1, dont les lancements sont enregistrés sans limite.
- **L'avancement d'une recherche dit son étape.** Chaque `SearchProgress` porte `step` (`search`, `dedupe`, `evaluate`, `save`), et selon l'étape des compteurs ou le verdict de la page évaluée (`title`, `kept`). Le front s'appuie dessus pour allumer les étapes et tenir ses compteurs (`core/search-run.service.ts`) : ne pas lui faire lire `message`, qui n'est qu'un texte à afficher. Un nouveau nœud du graph demande une valeur de `SearchStep`, côté Python et dans `api.models.ts`.
- **Le front lit le flux d'une recherche avec `fetch`, pas `EventSource`**, qui ne sait pas envoyer un `POST`. Si le flux se ferme sans bilan, il dit que la recherche continue sur le serveur, ce qui est vrai (voir le point suivant).
- **Une recherche lancée par l'API va au bout.** `api/routers/searches.py` la fait tourner dans son propre fil : si le navigateur ferme la connexion, les pages déjà payées sont quand même enregistrées. Un redémarrage du serveur, lui, l'interrompt.
- **Une seule recherche à la fois par utilisateur.** `SearchService.stream_search` refuse la seconde (409) avant de compter le quota, et `RunningSearch` libère la place à la fin, à l'échec, ou si le déroulement n'est jamais lu. La liste des recherches en cours est en mémoire, ce qui tient parce qu'un seul processus sert tout. `/api/me` le dit (`search_running`) : après un rechargement, le front ne peut plus suivre la recherche, il désactive le lancement et interroge `/api/me` jusqu'à sa fin, puis recharge ses listes (`SearchRunService.background`).
- **Un CV refusé laisse le précédent en place.** `CvIngestion.ingest` lit le PDF avant toute écriture, et `CvService.save_cv` enregistre le texte et vide les rejets dans la même transaction. Garder cet ordre.
- **Le PDF valide des tests est `tests/fixtures/cv.pdf`.** C'est le CV de l'auteur, versionné : la fixture `valid_pdf` et les tests de bout en bout s'en servent. Il n'entre pas dans l'image Docker.
- **Les dates sont en UTC, avec leur fuseau.** `created_at` et `applied_at` viennent de `CURRENT_TIMESTAMP` ; les services les renvoient en `datetime` UTC. La conversion en heure de Paris se fait à l'affichage, dans le front (`ParisDatePipe` de `core/paris-date.pipe.ts`) : le `DatePipe` d'Angular n'accepte qu'un décalage fixe, faux la moitié de l'année.
- **Le fuseau horaire vient d'un paquet.** Le quota journalier se compte à l'heure de Paris, avec `zoneinfo`, qui a besoin des données de `tzdata` : ni Windows ni l'image Docker ne les fournissent. Ne pas retirer `tzdata` des dépendances, même si rien ne l'importe.
- **Pousser sur `main` met en ligne.** Le workflow lance le linter et les tests, puis déploie et redémarre l'instance, ce qui interrompt une recherche en cours et applique les migrations en attente à la base en ligne. Ne pas pousser sans l'accord de l'utilisateur.
- **En ligne, la machine est mise en veille, pas arrêtée.** `auto_stop_machines = 'suspend'` (`fly.toml`) : sans visite, Fly fige la machine et la reprend en une seconde, mémoire comprise, sans relancer Python. Elle ne redémarre vraiment qu'à un déploiement, ou si Fly a perdu son instantané. Rien ne doit donc compter sur un redémarrage fréquent. Au réveil, l'horloge retarde de quelques secondes : `CLOCK_SKEW_SECONDS` (`api/security.py`) évite qu'un jeton Google tout juste émis soit refusé. La veille exige au plus 2 Go de mémoire et pas de swap. Pour le démarrage à froid qui reste, le `Dockerfile` précompile le code Python.
- **Sur Fly.io, seul `/data` survit à un redémarrage.** Le reste du disque est remis à zéro, et le volume monté sur `/data` (section `[mounts]` de `fly.toml`) n'est pas partagé entre machines. Tout fichier à conserver doit passer par `DATA_DIR`, et l'application doit rester sur une seule machine.
- **Les textes de `api/legal/` décrivent le comportement réel.** Données enregistrées, envoi du CV à OpenAI et coordonnées qui en sont retirées, quota, copies de sauvegarde, suppression de compte, durée de conservation, nom et photo Google gardés dans le cookie : les mettre à jour quand l'un de ces points change.
- **Le mot de passe donne les données du propriétaire.** Sans connexion Google, `APP_PASSWORD` désigne l'utilisateur 1. Dès que `GOOGLE_CLIENT_ID` est défini, il n'ouvre plus rien, et une session ouverte avec lui ne vaut plus (`read_session_token`).
- **Un compte supprimé garde sa ligne, vide.** `AccountService.delete_account` efface le CV et les lignes de l'utilisateur dans chaque table, y compris dans les copies d'avant migration, puis retire l'adresse de sa ligne de `users` sans la supprimer : SQLite redonnerait son identifiant au compte suivant, qui hériterait de ce qu'une recherche encore en cours aurait écrit. Pour la même raison, la suppression est refusée pendant une recherche (`SearchService.is_running`). Une nouvelle table qui porte `user_id` doit être vidée dans `delete_account`. Le propriétaire peut effacer ses données, mais garde l'identifiant 1.
- **Un compte d'invité inactif est supprimé par le serveur, une fois par jour.** `AuthService.resolve_user_id` date la dernière activité d'un invité (`users.last_seen_at`), au jour près pour ne pas écrire à chaque requête. `AccountService.delete_inactive_accounts_if_due` supprime ceux restés `INACTIVE_ACCOUNT_DAYS` sans activité, au plus une fois par jour : il n'y a pas de tâche planifiée, c'est `create_app()` au démarrage et chaque requête identifiée (`get_current_caller` de `api/security.py`) qui l'appellent. Le démarrage seul ne suffit pas : la machine en ligne est mise en veille, pas arrêtée, et reprend sans redémarrer. L'appel vient après l'identification, pour qu'un invité de retour ne soit pas supprimé par sa propre visite. Un échec est journalisé sans faire échouer la requête. Le propriétaire n'est jamais concerné. Les règles de confidentialité affichent la durée à partir de cette constante ; la page Compte du front, elle, écrit « un an » en dur.
- **L'identifiant 1 est réservé au propriétaire.** La première migration insère la ligne 1 de `users` sans adresse, pour qu'aucun invité ne reçoive cet identifiant et les données d'avant les comptes. Le propriétaire est reconnu par `OWNER_EMAIL`, pas par la table.

## Conventions

- Commentaires, docstrings, messages de log et textes du front sont en français ; les noms de variables et de fonctions sont en anglais.
- Les commentaires expliquent le pourquoi, pas le quoi, et restent rares.
- Une transaction, c'est un `with self.database.session() as session` dans une méthode de service ou un nœud du graph : elle est validée en sortie, annulée en cas d'erreur. Un dépôt reçoit la session et ne valide jamais lui-même.
- Les dépôts renvoient des modèles SQLAlchemy en lecture, et un booléen ou un nombre de lignes en écriture. Les services renvoient des schémas Pydantic.
- Une règle métier (quota, validation, enchaînement de deux dépôts) s'écrit dans un service, jamais dans `api/` ni dans le front. Les méthodes d'un service prennent `user_id` en premier paramètre.
- Les erreurs destinées à l'utilisateur sont des sous-classes d'`AppError` (`errors.py`) avec un message en français, renvoyé tel quel par l'API et affiché tel quel par le front (`core/api-error.ts`). Une nouvelle sous-classe reçoit son code HTTP dans `STATUS_CODES` de `api/main.py`.
- Une dépendance extérieure payante ou en réseau passe par un port de `agent/ports.py` (ou un équivalent), pour que les tests y branchent un faux.
- Mettre à jour le README quand une commande, une route, une table ou un réglage change.
